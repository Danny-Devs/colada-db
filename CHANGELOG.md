## [2026-07-22] — DAN-647: dispose() racing an in-flight flush no longer silently drops the post-drain residue (branch `tackle/dan-647-dispose-flush-lostwrite`)

- [fix] `persist.ts` — the one true data-loss bug in the dispose seam (spec-then-fix on the durability seam; RE-VET confirmed pre-existing at `343666e` with an executed gated-`writeBatch` repro, both `set` and `remove` flavors). `dispose()` ran `finalFlush = flush()` then `disposed = true`. When a prior flush was in flight (parked in `await engine.writeBatch`), the final `flush()` took the `if (flushing) { await inflightFlush; return flush(); }` path — and the re-entrant `flush()` then bailed on `if (!opened || disabled || disposed) return` now that `disposed` had flipped true. The in-flight batch's tail recovery `if (dirtySaves.size>0) scheduleFlush()` was defeated by the SAME flag (`scheduleFlush` short-circuits on `disposed`). A `set(Y)`/`remove(Y)` that entered the dirty sets AFTER the prior drain parked was silently non-durable — no error. Only real async engines expose it (a synchronous engine resolves `writeBatch` before dispose runs, so `flushing` is already false); same "world held still across an async gap" family as ADR-012–016, the gap here being the in-flight batch and the shifted state being `disposed` itself.
- [feat] ADR-017 semantics: **the dispose final flush survives its own `disposed` guard.** `flush` gains an internal `final` param (default `false`); the guard becomes `(disposed && !final)` and the re-entrant call propagates it (`return flush(final)`). `dispose()` calls `flush(true)`; every other caller (public handle, debounce timer, gc-sweep flush-first, `visibilitychange`/`beforeunload` listeners) calls `flush()`. `disposed` is still set SYNCHRONOUSLY in dispose — so every boot/hydration post-`await` `disposed` re-check keeps firing exactly as before (the alternative, deferring `disposed` until the flush resolves, was rejected precisely because it reopens those boot guards for a dispose racing boot: retention/hydration could outlive the coordinator). The public handle exposes `flush: () => flush()`, making `final` unreachable from outside the module — so a post-dispose external `flush()` still no-ops under `disposed` and a post-dispose `set` can't sneak a batch in (`unsub()` + the subscriber's `disposed` guard). Single-write per key (drain is a move; dirty/in-flight sets are disjoint per key). Alternatives weighed and rejected in the ADR: defer-`disposed` (reopens boot guards), a module-level `finalizing` flag (needs an un-set point or a post-dispose external flush bypasses the guard — the param sidesteps the fuzzy lifetime), disposed-immune tail `scheduleFlush()` (re-introduces a post-teardown timer dispose deliberately clears).
- [test] `src/dispose-flush.spec.ts` (4) — gated-`writeBatch` `slowEngine`: set-in-flight residue durable across dispose + remove-in-flight residue durable across dispose (**three verified FAILING pre-fix**: `contact:2` dropped on the save leg, its delete dropped on the remove leg, and — because the drop also breaks it — the single-write case) + one contract pin (a `set` arriving AFTER dispose never reaches disk and the external `flush()` is a no-op — no post-dispose sneak-in, exactly one batch runs). The single-write property (final flush writes the residue key exactly once — no double-flush) is asserted on the post-fix tree.
- [docs] ADR-017 (`docs/adr/017-dispose-final-flush-survives-the-disposed-guard.md`, amends ADR-014's "dispose racing boot/unload MUST flush acknowledged dirt" boundary — the flush that boundary depends on was itself lossy under the in-flight interleaving); LESSONS.md entry (a lifecycle flag that stops NEW work must not also stop the in-flight work's own completion — exempt the final drain, don't defer the flag); `flush` and `dispose` doc comments now state the honored contract.
- [review] Self-review sweep: post-dispose external set rejected (test 4 — `unsub()` detaches the subscriber AND `disposed` guards it; external `flush()` no-ops, zero extra batches); no double-flush (test 3 — per-key writeBatch touch-count == 1; drain-as-move keeps dirty/in-flight disjoint); dispose idempotent (second dispose returns at `if (disposed) return` — unchanged, durability.spec pin green); dispose-during-boot still guarded (no boot-path code touched, `disposed` still synchronous, all post-`await` re-checks fire — boot-hydration-writes.spec green); dispose with NO flush in flight (fastEngine `dispose() performs a final flush` pin green); dispose when disabled (`finalFlush = opened && !disabled ? … : Promise.resolve()` — no flush attempted); re-entrancy termination (post-dispose no new external batch starts and the gc timer is cleared, so the final chain drains the residue once and the next `flush(true)` sees `size 0` → returns — no infinite loop); in-flight-batch-fails leg (re-entrant `flush(true)` bails on `disabled`, fail-closed — engine dead, memory already sole copy).
- Verified: `CI=true pnpm -r test` 343/343 (310 → 314 core, +4; 29 mcp unchanged), `pnpm -r typecheck` / `pnpm -r lint` / `pnpm -r build` all green. ## [2026-07-21] — DAN-635: the optimistic mask now covers PUTs — an evicted optimistic put can no longer be paged over by a stale engine row (branch `tackle/dan-635-tx-foreign-interference`)

- [fix] `persist.ts` — closes flavor A of the tx-vs-foreign-writes family that ADR-015 filed as the follow-up (spec-then-fix on the durability seam; verified pre-existing at `71fdf82`, byte-identical with/without ADR-015's overlay). The transaction layer assumes a tx-touched key is not concurrently evicted or non-tx-mutated mid-flight; that assumption was unenforced and silent. **Flavor A (the must-fix — divergence SURVIVES settlement):** `tx.set(c1,"kept")` → `evict(c1)` mid-tx → `hydrateScope` pages the stale pre-tx engine row `v1` over the optimistic projection (fresh-wins via `store.has` protected the optimistic put ONLY while it stayed resident — eviction removed it, and the delete-only ADR-015 mask did not fire for a PUT). After commit, "kept" graduated to disk while memory kept `v1`: **memory `v1` / disk "kept" for the rest of the session.**
- [feat] ADR-016 semantics: **the optimistic mask covers any buffered op, not just deletes.** `hydrateRow`'s mask changes from `buffer.get(key)?.op === "delete"` to `buffer.has(key)` (one predicate), keeping mask-first precedence. A buffered PUT now vetoes hydration of its evicted key exactly as a buffered DELETE vetoes un-deletion — so a stale engine row can never page over an evicted optimistic put (flavor A dead by construction). After eviction memory is legitimately absent (ADR-004 cold row); on commit the tx op graduates and the next hydrate pages the committed value → **memory converges to the same truth disk converges to, by settlement.** No new state, no store coupling, no commit-contract change, no serverTruth touch — the change lives entirely in the read-side overlay and cannot affect the write path, the sync outbox (ADR-006 §1), or the flush pipeline.
- [feat] **Flavor B (foreign confirmed non-tx write racing a tx-touched key) is bounded, not fixed — deliberately.** The mask stays mask-first: a foreign confirmed write must NOT override it, because preferring it (candidate d) would diverge at COMMIT (the tx op graduates to disk while memory keeps the foreign value). What remains is the rollback clobber — the tx `serverTruth` snapshot goes stale the instant a foreign confirmed write lands, and rollback restores the stale snapshot over it (memory reverts to pre-tx `v1`, disk keeps the confirmed `v2`). That is a serverTruth-staleness hazard owned by the sync coordinator's server-authoritative rebase (ADR-006 §6), byte-identical pre/post this ADR, now NAMED and pinned rather than silent. Alternatives weighed and rejected in the ADR: mask-yields-to-confirmed (breaks commit-coherence — the flavor-B commit-leg pin encodes exactly this), evict-immunity (manual `store.evict` bypasses refcounts so it doesn't fix the repro; couples store to transactions; tx-holds-memory-hostage risk), settlement reconciliation (commit is event-silent by design — re-applying means new events + a subscriber loop, or forbidden silent memory correction; and it only covers commit, not the mid-tx window), and serverTruth-refresh-on-foreign-write (widens the tx conflict model into the frozen sync-outbox machinery ahead of the coordinator that owns it).
- [test] `src/tx-foreign-interference.spec.ts` (5) — flavor A with a mid-tx remount (the stale row must not resurrect; memory then converges to "kept" across commit+reboot) + no-remount pin (evict-then-commit converges cleanly) + flavor-A rollback leg (memory and disk both stay at server truth); flavor-B commit-leg pin (the delete mask keeps memory consistent with the committed delete — this pin IS the rejection of candidate d) + flavor-B rollback-leg pin (the BOUNDED divergence: foreign write survives to disk, clobbered in memory on rollback). **Pre-fix failure pinned: 2/5 verified failing against the unfixed source** (both flavor-A `store.has` masking assertions returned `true` — the stale `v1` paged in; the 3 pins pass by design pre and post).
- [docs] ADR-016 (`docs/adr/016-optimistic-put-mask-and-the-foreign-write-boundary.md`, amends ADR-015 rule 4); ADR-015's rule-4 boundary paragraph now points at ADR-016 as the resolution of the evicted-put hole; LESSONS.md entry (a fresh-wins guard that depends on residency is not a mask — eviction is exactly the case it can't cover). `enablePersistence` docstring updated (the mask covers PUT and DELETE).
- [review] Self-review sweep: overlapping/nested txs touching one key (`buffer.has` vetoes if ANY open tx holds the key — correct while any is unsettled); `tx.set→evict→tx.set` again (re-adds to memory + buffer, mask still vetoes on a subsequent evict); manifest keys never enter `pendingTx` so `readManifestRow` is untouched; synthesis path (rule 3) only fires for keys with a dirty/in-flight save — a tx-buffered key has neither, and hydrateRow re-derives the mask so it can't leak; dispose mid-tx (`pendingTx.clear()` then `disposed` gates all hydration); fresh-wins still last (resident optimistic puts blocked by `store.has`, mask matters only once residency is lost). No existing test asserted an evicted-optimistic-put key pages in the engine row (that would assert the bug) — the broadened mask leaves all 305 prior core tests green.

## [2026-07-21] — DAN-629: the pending-truth overlay now covers the in-flight window (branch `tackle/dan-629-inflight-overlay`)

- [fix] `persist.ts` — closes the persist.ts in-flight-window family (spec-then-fix on the durability seam; the boundary both ADR-013 and ADR-014 documented as "the in-flight-overlay follow-up"). `flush()` drained `dirtySaves`/`dirtyDeletes` synchronously at entry, BEFORE `await engine.writeBatch` — so for the batch's whole flight, confirmed-but-undurable truth was invisible to `hydrateRow`'s overlay and to `readManifestRow`. Executed flavors, all in-session divergence (disk/reboot stayed correct): a `hydrateScope` racing an in-flight delete resurrected the removed entity into memory for the rest of the session (worst); an in-flight save + evict paged stale v1 back while disk converged to v2; a never-flushed entity evicted pre-flush was invisible to `hydrateScope` (engine has no row, so the overlay had nothing to overlay); the module's own `visibilitychange`/`beforeunload` listeners calling `flush()` mid-boot made a hidden tab an AUTOMATIC entry (DAN-630 gauntlet F1 — sharpest: the delete was drained AND durably acked before boot's stale load snapshot resolved); and `tx.remove()` racing boot let the stale snapshot un-delete an optimistic projection mid-transaction, leaving memory keeping a row disk deletes after commit (gauntlet F2).
- [feat] ADR-015 semantics: **pending truth ends only at durable acknowledgment.** (1) Drain is a MOVE, not a clear — the drained batch lands in `inflightPuts`/`inflightDeletes`, and the overlay precedence is: open-tx delete mask → dirty (newest confirmed) → in-flight (drained, possibly acked) → engine row. (2) Clearing is quiescence-gated (`maybeClearInflight`): no batch in flight AND boot settled AND no `hydrateScope` bracket open — this, not mere in-flight tracking, is what closes F1 (an acked delete must stay visible to a straddling stale snapshot); on engine failure the overlay is never cleared (frozen record of truth the engine lost keeps the session's hydrations honest). (3) `hydrateScope` synthesizes manifest-declared keys whose only copy is a pending save (dirty or in-flight) — the manifest declares residency, so the set→evict-before-first-flush window can no longer hide an entity. (4) An uncommitted optimistic DELETE masks hydration of its key (amends ADR-013's pendingTx note: unconfirmed state still never flushes/never hydrates, but it can VETO hydration); commit graduates normally, rollback lifts the mask. Optimistic PUTs need no mask (fresh-wins already blocks). `readManifestRow` consults the full overlay and re-checks AFTER its engine read (a manifest write landing mid-load outranks the loaded row). Alternatives weighed and rejected in the ADR: per-read overlay snapshot (misses truth confirmed mid-read-flight — exactly F1); awaiting the in-flight batch before hydration reads (drain-mid-read hole remains, adds latency); engine-level read-ordering contract (protocol change, DO-NOT-TOUCH); bounding F2 to tx-graduation semantics (the mask is projection integrity, not graduation — commit/rollback flows untouched).
- [test] `src/inflight-overlay.spec.ts` (11) — new `gateWrites` idiom (holds `writeBatch` in flight; reads pass through) + `gateBootStale` (captures load rows EAGERLY then holds delivery — the stale-snapshot interleaving `gateBoot` cannot produce): delete-in-flight no-resurrection (memory + disk + reboot); save-in-flight pages v2 not stale v1; in-flight manifest row outranks the engine's stale manifest (no retention resurrection under a dropped reference); synthesis dirty + synthesis in-flight; mid-boot remove + direct flush not resurrected by the stale boot snapshot (F1); mid-boot set+flush+evict hydrates the retained v2 (the DAN-621 staleness class reopened through the acked window); F2 commit leg (mask holds, memory and disk agree post-commit) + rollback leg (mask lifts, untouched durable row pages back in); two pins (flush concurrency contract unchanged; quiesced overlay does not shadow newer durable truth across two full flush cycles). **Pre-fix failure pinned: 9/11 verified failing against the unfixed source** (the 2 pins pass by design).
- [docs] ADR-015 (`docs/adr/015-pending-truth-ends-at-durable-ack.md`); ADR-013's boundary bullet and pendingTx note + ADR-014's direct-flush boundary bullet now point at the closure; LESSONS.md entry (drain-then-await hides truth — a drain in an async pipeline must stay observable until quiescence); stale `booting`/scheduleFlush comments updated to the ADR-015 division of labor (timer deferral = churn economy + first line; retained overlay = the guarantee).
- [review] Self-review sweep: overlapping flushes (`flushing` serializes batches; the await-then-reflush recursion merges consecutive drains into the in-flight sets, latest-op-per-key); hydrate racing flush's `finally` (the `activeHydrations` bracket spans read AND consume, so the finally's clear defers — decrement-then-clear happens only after the hydrate loop consumed its rows); dispose mid-flight (dispose's final flush drains pre-`disposed=true`, clears at its own finally; an open hydrateScope bracket defers that clear and its own post-await `disposed` check returns 0); gc sweep (flush-first unchanged; sweep evicts only after ack, and a subsequent hydrateScope reads post-batch engine state or the retained overlay — same values); memory growth (in-flight sets hold references to the already-encoded values the dirty sets held — no copies; transiently bounded by keys flushed since last quiescent instant, freed at first idle; degraded mode retains at most the final batch); encode/decode symmetry (in-flight values are the same encoded objects, `hydrateRow` decodes uniformly; manifest rows stay raw on both paths, never reach `hydrateRow`). Bounded in the ADR, not fixed: "all"-mode boot does not synthesize (mid-boot set→manual-evict with no manifest stays cold until its flush lands — no scope declared residency, gc timers defer during boot); boot's manifest-INDEX/scope-row loads stay engine-direct (a manifest write racing boot via direct flush can stale the boot scope SET; every entity row is still individually reconciled; converges via preload/hydrateScope).

## [2026-07-21] — DAN-630: boot hydration silently dropped app writes racing the engine loads (branch `tackle/dan-630-boot-hydration-write-drop`)

- [fix] `persist.ts` no longer drops app writes that land while boot hydration's engine loads are in flight (spec-then-fix on the durability seam; the hole DAN-621's self-review flagged as "found, NOT fixed"). Boot held `isHydrating = true` across every `engine.loadMany`/`engine.loadAll` await and the subscriber early-returned on ANY event under the flag — so a legitimate `set`/`remove` landing in that window (real width: IDB/SQLite load latency; apps that write on startup hit it routinely) emitted its event, was applied to memory, and never entered the dirty sets: silently non-durable, no error. The flag's SPAN was the defect, not its existence — and because the early-return sat before the transactional branch, mid-boot optimistic writes were silently dropped from the tx buffer too (a committed transaction then "graduated" a hole).
- [feat] ADR-014 semantics: **hydration exclusion by provenance, not coordinator phase.** (1) The subscriber excludes exactly the events stamped `origin: "hydration"` — the stamp hydrateRow already mints through the privileged `runWith` channel (ADR-007 §1, pinned by `origin.spec.ts`); the `isHydrating` flag is deleted outright (boot's span AND `hydrateScope`'s try/finally choreography). Provenance travels with the event, so there is no instant at which an app write is invisible to the durability pipeline — and the exclusion is robust even to a future async/batched subscribe, since origin is stamped into the event at emission. Mid-boot writes then flow into the dirty sets where the ADR-013 pending-truth overlay + fresh-wins already reconcile them against stale engine rows: `hydrateRow` skips a mid-boot-removed key (no resurrection) and `store.has` keeps a mid-boot set from being clobbered in memory. (2) The debounce and gc timers DEFER (re-arm) while boot hydration is in flight: flushing mid-boot would drain a pending delete out from under the overlay while a load snapshot predating it is still in the engine — the stale row would hydrate unopposed. Explicit `flush()` keeps its current mid-boot semantics (dispose racing boot must still flush acknowledged dirt); that residual direct-call window is the pre-existing in-flight class ADR-013 already documents, now narrowed to direct `flush()` calls (app code or the visibilitychange/beforeunload lifecycle listeners — see ADR-014's boundary bullet). Alternatives weighed and rejected in the ADR: tight-scoping the flag around the synchronous loops (behaviorally equivalent today but keeps the invariant temporal — this bug WAS the span drifting); buffer-and-replay (a second queue with its own ordering/failure semantics for a problem provenance dissolves); origin filter without the deferral (leaves the timer path open to stale-snapshot resurrection).
- [test] `src/boot-hydration-writes.spec.ts` (8) — gated-engine boot idiom (loads held unresolved, predicate-selectable so manifest tests can hold a specific boot load): all-mode mid-boot set durable after flush+reboot; all-mode mid-boot remove durable AND not resurrected into memory by the stale snapshot; mid-boot write to a stale-snapshot key wins in memory and on disk; mid-boot write auto-flushes with no explicit flush (the deferral re-arm strands nothing); manifest-mode writes during the index load (durable + clobber-proof, both fresh-wins legs asserted); manifest-mode remove during the entity-rows load (tightest window — after manifests resolved, before hydrateRow); two behavior pins (boot hydration and hydrateScope remount produce zero engine puts — no write-storm). **Pre-fix failure pinned: 6/8 verified failing against the unfixed source** (the 2 passers pin the hydration-exclusion behavior that must survive the mechanism swap).
- [docs] ADR-014 (`docs/adr/014-hydration-exclusion-by-provenance.md`); LESSONS.md entry (an exclusion window keyed to a phase flag is a span bug waiting to happen — key exclusions to provenance).
- [review] Self-review sweep: dispose() racing boot (post-await `disposed` re-checks unchanged; dispose's final flush still runs mid-boot and boot can never hydrateRow after it — the sync hydrate loops can't interleave with dispose); pre-open dirt (timer now re-arms under `booting` instead of stranding against `!opened`; the post-boot re-schedule retained as second line); re-armed timer vs post-boot re-schedule (scheduleFlush no-ops on a pending timer — no double-fire); boot failure paths (open reject → catch clears `booting` and sets `disabled`, killing the re-arm loop; load reject → `finally` clears `booting` before the catch); `removedPreBoot`/manifest verbs unaffected (they write the dirty sets directly, never rode the subscriber); INDEX_KEY (never reaches `hydrateRow` in either mode; the timer deferral also removes the automatic path into review-B1's half-seeded-index materialization — explicit-flush path pre-existing, unchanged); listener-writes-during-hydration-delivery inherit the hydration origin via the runWith stack and stay excluded, byte-for-byte the old flag behavior, now visible in the event stream.

## [2026-07-21] — DAN-621: evict cancelled the pending save — stale durable-row resurrection (branch `tackle/dan-621-persist-resurrection`)

- [fix] `persist.ts` no longer resurrects dead-lineage state after remove→set→evict within one debounce window (spec-then-fix on the durability seam; found pre-existing by the DAN-620 land gauntlet, verified at `699a951` with plain events — no `clear()` involved). The old evict branch dropped any pending save under ADR-004's "last flushed value stands" economy; that drop is sound only while the durable row holds some prior confirmed value of a SURVIVING entity — an intervening `remove` invalidates the row's lineage, and the subsequent set's save was the only thing scheduled to correct it. Cancelling it made the next boot re-hydrate the pre-remove value.
- [feat] ADR-013 semantics: **eviction has no authority over the durability pipeline.** (1) `evict` never mutates the dirty sets — a pending confirmed write always flushes; the pipeline is monotone in confirmed store truth (a dirty entry is displaced only by a newer confirmed event for its key). This kills the plain, transactional (committed remove→set net-put), and clear()-flavored (ADR-012 reentrant re-write) resurrection variants at once, with zero new state, and upgrades what re-hydrates from "last flushed value" to "last confirmed value" (plain set→evict no longer silently discards a debounce window of confirmed updates). (2) Engine reads honor the pending-truth overlay (`readManifestRow`/B4 generalized to entity rows): `hydrateRow` skips keys with a pending delete (boot can't resurrect a row the session already removed) and prefers a pending save's value over the stale engine row (evict→`hydrateScope` remount inside the dirty window pages in the confirmed value). Uncommitted `pendingTx` buffers deliberately excluded — unconfirmed state neither flushes nor hydrates. Alternatives weighed and rejected in the ADR: taint-gated cancel (new bookkeeping lifecycle incl. per-transaction removed-key tracking, all to preserve an economy that is nearly dead code — the only gc trigger pre-flushes, so the drop only ever fired on manual evicts, exactly where it was dangerous); delete-carry-through (all three engines apply puts THEN deletes — a same-key put+delete batch destroys the re-set value; fixing that means touching the engine protocol); dirty-generation counter (taint semantics, heavier machinery).

## [2026-07-21] — DAN-620: clear() reentrancy — atomic snapshot semantics, no silent wipe (branch `tackle/dan-620-clear-reentrancy`)

- [fix] `store.clear()` is now reentrant-safe (spec-then-fix, the DAN-602/0.3 pattern — semantics decided and filed BEFORE the patch). The old shape (per-type id drain → trailing `typeMap.clear()` + `refCounts.clear()`) silently erased any write a listener applied during the drain — applied, evented, then wiped with NO event, diverging every event consumer from store truth (executed repro: DAN-606 land gauntlet, finding 1) — and destroyed retention bookkeeping wholesale, including drain-time retains and the memory-absent cold-row pins `persist.ts`'s manifest-coordinator doc already promised survive a `clear()`.
- [feat] ADR-012 semantics: **clear() removes exactly its snapshot; reentrant writes survive.** All `(type, id)` entries are captured atomically at entry (the old lazy per-type snapshot gave a write to a later type different fate than one to an earlier type) and removed via the ordinary per-entity evented path — no bulk wipe of any kind. Refcount cleanup is keyed deletion for ALL snapshotted ids, completed BEFORE any emission begins (land-gauntlet F1 hoist — the per-turn variant destroyed CROSS-ID retains established during earlier deliveries: order-dependent behavior for one listener pattern, caught by the reviewer's executed repro and pinned by a regression test verified failing against it), so listener-established pins — same-id and cross-id — and cold-key pins survive; a snapshotted-but-not-yet-drained id touched mid-drain is still cleared, with the reentrant value as honest `previousData`. Alternatives (refuse-loudly; evented bulk wipe; decrement-by-snapshot-count) weighed and rejected in the ADR — refuse breaks the H5 listeners-may-write contract nondeterministically; decrement double-counts against scopes that self-release. Behavior shift documented: clear() guarantees "everything present at call time was removed and evented," not "empty on return" (identical when no listener writes); phantom refs minted mid-drain now survive (subscribe-before-data no longer silently severed); nested clear() safe by construction (inner snapshot removes, outer takes the C1 tombstone path).
