# Changelog

## [2026-07-21] — DAN-630: boot hydration silently dropped app writes racing the engine loads (branch `tackle/dan-630-boot-hydration-write-drop`)

- [fix] `persist.ts` no longer drops app writes that land while boot hydration's engine loads are in flight (spec-then-fix on the durability seam; the hole DAN-621's self-review flagged as "found, NOT fixed"). Boot held `isHydrating = true` across every `engine.loadMany`/`engine.loadAll` await and the subscriber early-returned on ANY event under the flag — so a legitimate `set`/`remove` landing in that window (real width: IDB/SQLite load latency; apps that write on startup hit it routinely) emitted its event, was applied to memory, and never entered the dirty sets: silently non-durable, no error. The flag's SPAN was the defect, not its existence — and because the early-return sat before the transactional branch, mid-boot optimistic writes were silently dropped from the tx buffer too (a committed transaction then "graduated" a hole).
- [feat] ADR-014 semantics: **hydration exclusion by provenance, not coordinator phase.** (1) The subscriber excludes exactly the events stamped `origin: "hydration"` — the stamp hydrateRow already mints through the privileged `runWith` channel (ADR-007 §1, pinned by `origin.spec.ts`); the `isHydrating` flag is deleted outright (boot's span AND `hydrateScope`'s try/finally choreography). Provenance travels with the event, so there is no instant at which an app write is invisible to the durability pipeline — and the exclusion is robust even to a future async/batched subscribe, since origin is stamped into the event at emission. Mid-boot writes then flow into the dirty sets where the ADR-013 pending-truth overlay + fresh-wins already reconcile them against stale engine rows: `hydrateRow` skips a mid-boot-removed key (no resurrection) and `store.has` keeps a mid-boot set from being clobbered in memory. (2) The debounce and gc timers DEFER (re-arm) while boot hydration is in flight: flushing mid-boot would drain a pending delete out from under the overlay while a load snapshot predating it is still in the engine — the stale row would hydrate unopposed. Explicit `flush()` keeps its current mid-boot semantics (dispose racing boot must still flush acknowledged dirt); that residual explicit-path window is the pre-existing in-flight class ADR-013 already documents, now narrowed to explicit calls only. Alternatives weighed and rejected in the ADR: tight-scoping the flag around the synchronous loops (behaviorally equivalent today but keeps the invariant temporal — this bug WAS the span drifting); buffer-and-replay (a second queue with its own ordering/failure semantics for a problem provenance dissolves); origin filter without the deferral (leaves the timer path open to stale-snapshot resurrection).
- [test] `src/boot-hydration-writes.spec.ts` (8) — gated-engine boot idiom (loads held unresolved, predicate-selectable so manifest tests can hold a specific boot load): all-mode mid-boot set durable after flush+reboot; all-mode mid-boot remove durable AND not resurrected into memory by the stale snapshot; mid-boot write to a stale-snapshot key wins in memory and on disk; mid-boot write auto-flushes with no explicit flush (the deferral re-arm strands nothing); manifest-mode writes during the index load (durable + clobber-proof, both fresh-wins legs asserted); manifest-mode remove during the entity-rows load (tightest window — after manifests resolved, before hydrateRow); two behavior pins (boot hydration and hydrateScope remount produce zero engine puts — no write-storm). **Pre-fix failure pinned: 6/8 verified failing against the unfixed source** (the 2 passers pin the hydration-exclusion behavior that must survive the mechanism swap).
- [docs] ADR-014 (`docs/adr/014-hydration-exclusion-by-provenance.md`); LESSONS.md entry (an exclusion window keyed to a phase flag is a span bug waiting to happen — key exclusions to provenance).
- [review] Self-review sweep: dispose() racing boot (post-await `disposed` re-checks unchanged; dispose's final flush still runs mid-boot and boot can never hydrateRow after it — the sync hydrate loops can't interleave with dispose); pre-open dirt (timer now re-arms under `booting` instead of stranding against `!opened`; the post-boot re-schedule retained as second line); re-armed timer vs post-boot re-schedule (scheduleFlush no-ops on a pending timer — no double-fire); boot failure paths (open reject → catch clears `booting` and sets `disabled`, killing the re-arm loop; load reject → `finally` clears `booting` before the catch); `removedPreBoot`/manifest verbs unaffected (they write the dirty sets directly, never rode the subscriber); INDEX_KEY (never reaches `hydrateRow` in either mode; the timer deferral also removes the automatic path into review-B1's half-seeded-index materialization — explicit-flush path pre-existing, unchanged); listener-writes-during-hydration-delivery inherit the hydration origin via the runWith stack and stay excluded, byte-for-byte the old flag behavior, now visible in the event stream.
- Verified: `CI=true pnpm -r test` 323/323 (286 → 294 core, +8; 29 mcp unchanged), `pnpm -r typecheck` / `pnpm -r lint` / `pnpm -r build` all green. Scope note: engines/, sqlite-worker.ts, matcher/matcher-view, transactions.ts untouched — the fix is 8 hunks in `src/persist.ts`, net −4 lines of mechanism.

## [2026-07-21] — DAN-621: evict cancelled the pending save — stale durable-row resurrection (branch `tackle/dan-621-persist-resurrection`)

- [fix] `persist.ts` no longer resurrects dead-lineage state after remove→set→evict within one debounce window (spec-then-fix on the durability seam; found pre-existing by the DAN-620 land gauntlet, verified at `699a951` with plain events — no `clear()` involved). The old evict branch dropped any pending save under ADR-004's "last flushed value stands" economy; that drop is sound only while the durable row holds some prior confirmed value of a SURVIVING entity — an intervening `remove` invalidates the row's lineage, and the subsequent set's save was the only thing scheduled to correct it. Cancelling it made the next boot re-hydrate the pre-remove value.
- [feat] ADR-013 semantics: **eviction has no authority over the durability pipeline.** (1) `evict` never mutates the dirty sets — a pending confirmed write always flushes; the pipeline is monotone in confirmed store truth (a dirty entry is displaced only by a newer confirmed event for its key). This kills the plain, transactional (committed remove→set net-put), and clear()-flavored (ADR-012 reentrant re-write) resurrection variants at once, with zero new state, and upgrades what re-hydrates from "last flushed value" to "last confirmed value" (plain set→evict no longer silently discards a debounce window of confirmed updates). (2) Engine reads honor the pending-truth overlay (`readManifestRow`/B4 generalized to entity rows): `hydrateRow` skips keys with a pending delete (boot can't resurrect a row the session already removed) and prefers a pending save's value over the stale engine row (evict→`hydrateScope` remount inside the dirty window pages in the confirmed value). Uncommitted `pendingTx` buffers deliberately excluded — unconfirmed state neither flushes nor hydrates. Alternatives weighed and rejected in the ADR: taint-gated cancel (new bookkeeping lifecycle incl. per-transaction removed-key tracking, all to preserve an economy that is nearly dead code — the only gc trigger pre-flushes, so the drop only ever fired on manual evicts, exactly where it was dangerous); delete-carry-through (all three engines apply puts THEN deletes — a same-key put+delete batch destroys the re-set value; fixing that means touching the engine protocol); dirty-generation counter (taint semantics, heavier machinery).
- [test] `src/evict-resurrection.spec.ts` (9) — the F3 exact repro (memory engine, remove→set→evict→flush→reboot ⇒ survivor value), remove→set→evict→re-set, clear()-flavored (reentrant re-write during the drain then evict), transactional flavor (tx remove→set commit graduates a net-put, evict must not cancel it), set→set(v2)→evict freshness (pins the ADR-013 supersession of "last flushed value stands"), two delete-carry pins (remove→evict; remove→set→remove→evict), and the two overlay legs (pre-ready remove not resurrected at boot; hydrateScope inside the dirty window hydrates the pending value and it survives reboot). **Pre-fix failure pinned: 6/9 verified failing against the unfixed source** (the 3 passers deliberately pin behavior that already held: re-set-after-evict self-repairs, and both delete-carry cases).
- [docs] ADR-013 (`docs/adr/013-evict-has-no-authority-over-durability.md`, amends ADR-004's drop clause only — the evict/remove split is untouched); stale `scheduleGcSweep` comment updated (flush-first ordering retained as a durability-before-eviction nicety, no longer load-bearing); LESSONS.md entry (a cache-layer event must never cancel a truth-layer correction).
- [review] Self-review sweep: evict branch's early-return audited against every dirt-stranding path (pre-open dirt is rescued by the post-boot re-schedule; in-flight arrivals by flush's finally — nothing relied on evict's scheduleFlush); overlay⇔boot interaction (only pre-open confirmed dirt can exist during hydration; manifest keys never reach `hydrateRow`; INDEX_KEY enters dirtySaves only at flush materialization); encode/decode symmetry of pending values verified through both hydrateScope and reboot legs. **Pre-existing hole found, NOT fixed (own ticket needed):** boot's `isHydrating = true` spans the `loadAll`/`loadMany` awaits, so an app write landing during those awaits is silently dropped from persistence (subscriber early-returns) — a separate event-loss class, orthogonal to eviction; `hydrateScope` already scopes the flag correctly around its synchronous loop.
- Verified: `CI=true pnpm -r test` 315/315 (277 → 286 core, +9; 29 mcp unchanged), `pnpm -r typecheck` / `pnpm -r lint` / `pnpm -r build` all green. Scope note: engines/, sqlite-worker.ts, matcher/matcher-view, transactions.ts untouched — the entire fix is 3 hunks in `src/persist.ts`.

## [2026-07-21] — DAN-620: clear() reentrancy — atomic snapshot semantics, no silent wipe (branch `tackle/dan-620-clear-reentrancy`)

- [fix] `store.clear()` is now reentrant-safe (spec-then-fix, the DAN-602/0.3 pattern — semantics decided and filed BEFORE the patch). The old shape (per-type id drain → trailing `typeMap.clear()` + `refCounts.clear()`) silently erased any write a listener applied during the drain — applied, evented, then wiped with NO event, diverging every event consumer from store truth (executed repro: DAN-606 land gauntlet, finding 1) — and destroyed retention bookkeeping wholesale, including drain-time retains and the memory-absent cold-row pins `persist.ts`'s manifest-coordinator doc already promised survive a `clear()`.
- [feat] ADR-012 semantics: **clear() removes exactly its snapshot; reentrant writes survive.** All `(type, id)` entries are captured atomically at entry (the old lazy per-type snapshot gave a write to a later type different fate than one to an earlier type) and removed via the ordinary per-entity evented path — no bulk wipe of any kind. Refcount cleanup is keyed deletion for ALL snapshotted ids, completed BEFORE any emission begins (land-gauntlet F1 hoist — the per-turn variant destroyed CROSS-ID retains established during earlier deliveries: order-dependent behavior for one listener pattern, caught by the reviewer's executed repro and pinned by a regression test verified failing against it), so listener-established pins — same-id and cross-id — and cold-key pins survive; a snapshotted-but-not-yet-drained id touched mid-drain is still cleared, with the reentrant value as honest `previousData`. Alternatives (refuse-loudly; evented bulk wipe; decrement-by-snapshot-count) weighed and rejected in the ADR — refuse breaks the H5 listeners-may-write contract nondeterministically; decrement double-counts against scopes that self-release. Behavior shift documented: clear() guarantees "everything present at call time was removed and evented," not "empty on return" (identical when no listener writes); phantom refs minted mid-drain now survive (subscribe-before-data no longer silently severed); nested clear() safe by construction (inner snapshot removes, outer takes the C1 tombstone path).
- [review] Land gauntlet (fresh reviewer, executed repros incl. pre-fix verification of all 10 tests in a throwaway worktree): one BLOCKING find (the F1 cross-id retain window above — fixed via the hoist + regression test), two boundary clarifications folded into ADR-012 (F4 "survives" precision; F2 phantom-ref-before-clear punctures the cold-row-pin guarantee — semantic question routed to DAN-602), one PRE-EXISTING persist.ts find (remove→set→evict within one debounce window resurrects stale durable state — verified at `699a951` with no clear() involved) → cut as its own ticket. Perf measured: ~1.3–1.5× on a 10K-entity clear (old path was already per-entity evented; logout-scale, acceptable).
- [test] `src/clear-reentrancy.spec.ts` (11) — reentrant set of a snapshotted id / a novel id (same + new type), reentrant retain (+ pin-without-re-add), cold-row pin survival, stream replayability through a reentrant clear (replay = source, the event-ordering invariant), the DAN-606 finding-1 repro verbatim (live encodable matcher view + reactive re-add: view === store truth, integrity guard reports zero divergence, view's pin intact at exactly 1, dispose releases), mid-drain phantom-ref survival, nested clear(), no-listener baseline. **Pre-fix failure pinned: 7/10 verified failing against `699a951`** (the 3 passers deliberately pin behavior that already held: honest not-yet-drained clearing, nested-clear safety, empty baseline).
- [docs] ADR-012 (`docs/adr/012-clear-reentrancy-snapshot-semantics.md`); LESSONS.md created (first entry: snapshot-then-bulk-clear is never reentrant-safe when listeners can write — any unevented cleanup after a listener-visible loop is a divergence bug by construction).
- [review] Self-review adjacent-hole sweep: persist remove→set same-key ordering verified last-writer-wins (the reentrant survivor reaches disk correctly); listener-Set mutation mid-drain safe under JS Set iteration; nested clear() test-pinned. Out of scope, noted on DAN-620: matcher-view `dispose()` mid-drain (ADR-010 surface, DO-NOT-TOUCH here), clear()-inside-an-open-transaction erasure semantics (literally DAN-602's title; `history.spec.ts` pins today's caveat).
- Verified: `CI=true pnpm -r test` 306/306 (266 → 277 core, +11 incl. the F1 regression; 29 mcp unchanged), `pnpm -r typecheck` / `pnpm -r lint` / `pnpm -r build` all green; observe-run drives the BUILT `dist/index.mjs` through finding-1 end-to-end (view seed → reactive re-add during clear → view === store truth → zero divergence → refcount exactly 1 → stream replay reproduces state → cold-row pin survives): 9/9 checks PASS.
