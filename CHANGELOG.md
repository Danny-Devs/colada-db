# Changelog

## [2026-07-23] — DAN-649 review gauntlet: the guard shape was safe but NOT strippable, the lint tested containment instead of dominance, and `Symbol.for` opened an encode/decode asymmetry (branch `tackle/dan-649-publish-hygiene`)

Consolidated fix pass from a three-adversary review of the DAN-649 entry below. Eleven findings, each independently re-verified before implementation. Two classes dominate: **a fix that was correct at runtime and wrong at build time**, and **a lint that manufactured confidence it had not earned**.

- [fix] **The guard shape defeated dead-code elimination — all five sites changed.** `typeof process !== "undefined" && process.env?.NODE_ENV !== "production"` is perfectly safe at runtime and every semantic test passed against it, which is exactly why it survived review. But `@rollup/plugin-replace`, Vite's production `define`, and webpack `DefinePlugin` substitute the **literal** member expression `process.env.NODE_ENV`; a `?.` between `env` and `NODE_ENV` leaves nothing for a literal definer to find. Mechanically confirmed on the shipped artifact: `dist/index.mjs` contained `process.env?.NODE_ENV` 5× and `process.env.NODE_ENV` **0×**. Measured consequence on the canonical Rollup production chain: **+1,106 bytes minified, +400 gzipped, all five internal dev-warning strings leaked into the production bundle**, and five constant-folded reads became live runtime reads. The shape is now `typeof process !== "undefined" && process.env && process.env.NODE_ENV !== "production"` — strips cleanly under a literal definer AND tolerates a `process` shim with no `.env` (the plain conjunct evaluates falsy rather than throwing, which the bare `process.env.NODE_ENV` variant does not). Sites: `matcher-view.ts`, `engines/sqlite.ts`, `persist.ts` ×3. *(esbuild is NOT affected — verified: its `define` is AST-aware and folds the `?.` form too. The failing toolchains are the literal-substitution ones.)*
- [test] **The strippability pin — the durable half of this lesson, and the one no semantic test can reach.** `src/process-guard.spec.ts` now asserts that every extracted guard contains the literal substring `process.env.NODE_ENV`, plus a tree-wide check that no shipped source optional-chains between `process.env` and `NODE_ENV`, plus a positive control proving the detector fires on the broken shape. Without this pin the next agent "tidies" the guard back to optional chaining, every existing test stays green, and every downstream production bundle silently regresses — the two shapes are runtime-identical, so the entire existing suite is blind to the difference.
- [fix] **The lint rule tested CONTAINMENT, not DOMINANCE — false confidence, which is worse than no rule.** `isGuarded` called `subtreeHasCheck(parent.left, …)`, which walked the entire left subtree, so a `typeof` check *anywhere* in there whitelisted the read even when it did not control it. Proven: `(typeof window !== "undefined" || typeof process !== "undefined") && process.env…` passed both the lint and the companion regression, and still throws `ReferenceError` in a real browser realm (executed under `node:vm` with `window` present and `process` genuinely undeclared). Replaced with a real dominance check — recursing through `&&` only for positive guards and `||` only for negative ones (the exact dual), never through the opposite connective, a ternary, a call, or a parenthesized disjunction.
- [fix] **The lint rejected this repo's own house idiom and had no escape hatch — the two conditions that get a required gate deleted.** `src/persist.ts` guards `navigator` with an inverted early return and `src/engines/idb.ts` hoists its `indexedDB` check into a returned boolean; the rule accepted neither shape for `process`, and offered no suppression mechanism at all, so the only escape was removing it from `package.json`. Now: (a) `if (typeof process === "undefined") return|throw|continue|break;` dominates the remainder of its block; (b) simple same-file constant propagation makes `const HAS_PROCESS = typeof process !== "undefined"` a valid guard token — deliberately unscoped and non-transitive, qualifying only when the name is declared exactly once in the file, so it fails loud on ambiguity; (c) `// lint-ok: no-unguarded-process-env — <reason>` on the offending line or the one above, with a **mandatory** reason (a reasonless suppression is itself a violation, or the auditable hatch is just a mute button).
- [fix] **`globalThis.process` was invisible to both gates — and the rule's own message invited it.** `isNamePosition` exempted any identifier where `parent.name === node`, which swallowed the `process` in `globalThis.process`. The error message said "`process` is a Node global", so an engineer reaching for the portable-looking `globalThis.process.env.NODE_ENV` got a green lint and a green test — and a `TypeError: Cannot read properties of undefined` in the same place, on the same degradation path, for the same audience (executed and confirmed). Member reads off `globalThis` / `self` / `window` / `global` are now reported unless optional-chained *through* the global (`globalThis.process?.env?.NODE_ENV`) or dominated by a `typeof` / `in` check.
- [fix] **The rule's suggested-fix message prescribed the shape that breaks DCE** (2 sites: the module docstring and `MESSAGE`). The logic was fine; the *advice* steered every future fix straight into the defect above. It now prescribes the strippable form and states the reason in one sentence, because the fix hint is the highest-leverage string in the file — it is what the next author copies.
- [fix] **The CLI reported success on paths that do not exist.** `collectFiles` swallowed `statSync` ENOENT and `checkPaths` resolved args against the repo root rather than `process.cwd()`, so `node scripts/no-unguarded-process-env.mjs some-typo` printed ✓ and exited 0. Harmless for the bare `pnpm lint` invocation, fatal the moment the rule is wired into lint-staged, a pre-commit hook, or a changed-files CI step — a green tick over an empty scan. Now `console.error` + exit 2 on a missing target, with args resolved against the working directory and `DEFAULT_ROOTS` still anchored to the repo (new export: `resolveTargets`).
- [fix] **Extension allowlist and spec-exemption bypass.** `isLintable` required `extname === ".ts"` exactly, so `.tsx` / `.mts` / `.cts` shipped source was silently unscanned; widened to all four. Separately, `collectFiles` on a *file* target checked only the extension and never consulted `isLintable`, so naming a spec file directly linted it — contradicting the documented exemption, and precisely what a changed-files wiring does. File targets now route through the same gate.
- [fix] **`ENTITY_REF_MARKER` is now `Symbol.for("colada-db/entity-ref@1")`** — versioned. The unversioned registry key correctly made two copies of colada-db agree on ref identity (that benefit is real and was executed), but a global registry interns across **versions** as well as instances: a page with v1 + v2 would have v1's `isEntityRef` accept a v2 ref. The plain `Symbol()` it replaced degraded cross-version refs safely to opaque data, and that safety property was being traded away silently. The suffix keeps 100% of the duplicate-instance benefit within a major and restores fail-safe degradation across them. Bump it on any breaking change to the ref shape.
- [fix] **Closed the encode/decode asymmetry — this is what makes the versioned symbol safe.** The decode path validated the full ref shape with type checks (DAN-648/M2) while the encode path and `isEntityRef` checked only `record[ENTITY_REF_MARKER] === true`: the write path trusted exactly what the read path distrusted. A per-instance symbol had made that latent — a foreign-shaped ref was structurally unable to reach the encode branch. `Symbol.for` interns globally, so for the first time a ref minted by another copy satisfies the marker check, and an unvalidated encode destructively rewrites it into a malformed `__cdb_ref` row that decode's own M2 guard then permanently refuses — an unrecoverable relationship where pre-change it round-tripped intact. Both sites now mirror the M2 guard (`entityType`/`id`/`key` all `string`). Verified non-destructive; legitimate refs still resolve. **Severity, honestly: this requires two colada-db copies with *different* ref shapes on one page, i.e. a future major. The package is `0.1.0`, private, zero users on disk. A future hazard closed while it is free — not a live bug.**
- [feat] **`prepublishOnly": "pnpm build && pnpm typecheck && pnpm test && pnpm lint"`.** `dist/` is gitignored, `files` ships `dist`, and there was no `prepublishOnly` or `prepack` — so `npm publish` would ship whatever `dist/` happened to be sitting on disk, and a stale build from before this branch would publish silently and green. On a ticket whose entire premise is "the shipped artifact must behave correctly", the artifact was not tied to the committed source.
- [docs] **Two factually-wrong claims in `src/types.ts` corrected.** (1) The `Symbol.for` docstring justified itself by the chip-3 case where the Pinia Colada adapter carries its own engine copy. That is false — the frozen copy declares `Symbol("pinia-colada-entity-ref")`, a plain symbol with a *different description*, which `Symbol.for` cannot intern with. Reworded to the case actually closed (two `colada-db` copies deduped apart by npm — version skew, which chip 3's dependency swap makes possible), and states plainly that closing the frozen-copy case would need the plugin to adopt the same registry key. (2) "Changing this symbol therefore cannot affect any persisted data" was imprecise: the symbol value is never serialized, but symbol *identity* is the branch condition in `encodeEntityRefs`, so it determines disk **content**. Reworded — the value is never serialized, it gates encoding, single-instance emitted bytes are unchanged (verified byte-identical), so no migration is required.
- [docs] ADR-019 (`docs/adr/019-ref-identity-is-a-versioned-global-registry-key.md`) — the ref-identity contract, the version-suffix rule, and why symmetric validation is the thing that makes a global registry key safe. LESSONS.md gains two entries: the strippability lesson (an environment guard that is runtime-correct can still be build-time wrong, and no semantic test can tell) and the containment-vs-dominance lesson (a lint that tests containment manufactures false confidence, which is worse than no lint).

Every new lint capability carries a fixture AND a firing proof: the pre-gauntlet rule and the post-gauntlet rule were run side by side over 13 shapes — **13/13 land on the intended verdict, 8/13 are verdict CHANGES** (3a/3b/3c: REJECT → ACCEPT for the house idioms; 4/5: ACCEPT → REJECT for the shapes that crash). ## [2026-07-22] — DAN-647: dispose() racing an in-flight flush no longer silently drops the post-drain residue (branch `tackle/dan-647-dispose-flush-lostwrite`)

- [fix] `persist.ts` — the one true data-loss bug in the dispose seam (spec-then-fix on the durability seam; RE-VET confirmed pre-existing at `343666e` with an executed gated-`writeBatch` repro, both `set` and `remove` flavors). `dispose()` ran `finalFlush = flush()` then `disposed = true`. When a prior flush was in flight (parked in `await engine.writeBatch`), the final `flush()` took the `if (flushing) { await inflightFlush; return flush(); }` path — and the re-entrant `flush()` then bailed on `if (!opened || disabled || disposed) return` now that `disposed` had flipped true. The in-flight batch's tail recovery `if (dirtySaves.size>0) scheduleFlush()` was defeated by the SAME flag (`scheduleFlush` short-circuits on `disposed`). A `set(Y)`/`remove(Y)` that entered the dirty sets AFTER the prior drain parked was silently non-durable — no error. Only real async engines expose it (a synchronous engine resolves `writeBatch` before dispose runs, so `flushing` is already false); same "world held still across an async gap" family as ADR-012–016, the gap here being the in-flight batch and the shifted state being `disposed` itself.
- [feat] ADR-017 semantics: **the dispose final flush survives its own `disposed` guard.** `flush` gains an internal `final` param (default `false`); the guard becomes `(disposed && !final)` and the re-entrant call propagates it (`return flush(final)`). `dispose()` calls `flush(true)`; every other caller (public handle, debounce timer, gc-sweep flush-first, `visibilitychange`/`beforeunload` listeners) calls `flush()`. `disposed` is still set SYNCHRONOUSLY in dispose — so every boot/hydration post-`await` `disposed` re-check keeps firing exactly as before (the alternative, deferring `disposed` until the flush resolves, was rejected precisely because it reopens those boot guards for a dispose racing boot: retention/hydration could outlive the coordinator). The public handle exposes `flush: () => flush()`, making `final` unreachable from outside the module — so a post-dispose external `flush()` still no-ops under `disposed` and a post-dispose `set` can't sneak a batch in (`unsub()` + the subscriber's `disposed` guard). Single-write per key (drain is a move; dirty/in-flight sets are disjoint per key). Alternatives weighed and rejected in the ADR: defer-`disposed` (reopens boot guards), a module-level `finalizing` flag (needs an un-set point or a post-dispose external flush bypasses the guard — the param sidesteps the fuzzy lifetime), disposed-immune tail `scheduleFlush()` (re-introduces a post-teardown timer dispose deliberately clears).
- [test] `src/dispose-flush.spec.ts` (4) — gated-`writeBatch` `slowEngine`: set-in-flight residue durable across dispose + remove-in-flight residue durable across dispose (**three verified FAILING pre-fix**: `contact:2` dropped on the save leg, its delete dropped on the remove leg, and — because the drop also breaks it — the single-write case) + one contract pin (a `set` arriving AFTER dispose never reaches disk and the external `flush()` is a no-op — no post-dispose sneak-in, exactly one batch runs). The single-write property (final flush writes the residue key exactly once — no double-flush) is asserted on the post-fix tree.
- [docs] ADR-017 (`docs/adr/017-dispose-final-flush-survives-the-disposed-guard.md`, amends ADR-014's "dispose racing boot/unload MUST flush acknowledged dirt" boundary — the flush that boundary depends on was itself lossy under the in-flight interleaving); LESSONS.md entry (a lifecycle flag that stops NEW work must not also stop the in-flight work's own completion — exempt the final drain, don't defer the flag); `flush` and `dispose` doc comments now state the honored contract.
- [review] Self-review sweep: post-dispose external set rejected (test 4 — `unsub()` detaches the subscriber AND `disposed` guards it; external `flush()` no-ops, zero extra batches); no double-flush (test 3 — per-key writeBatch touch-count == 1; drain-as-move keeps dirty/in-flight disjoint); dispose idempotent (second dispose returns at `if (disposed) return` — unchanged, durability.spec pin green); dispose-during-boot still guarded (no boot-path code touched, `disposed` still synchronous, all post-`await` re-checks fire — boot-hydration-writes.spec green); dispose with NO flush in flight (fastEngine `dispose() performs a final flush` pin green); dispose when disabled (`finalFlush = opened && !disabled ? … : Promise.resolve()` — no flush attempted); re-entrancy termination (post-dispose no new external batch starts and the gc timer is cleared, so the final chain drains the residue once and the next `flush(true)` sees `size 0` → returns — no infinite loop); in-flight-batch-fails leg (re-entrant `flush(true)` bails on `disabled`, fail-closed — engine dead, memory already sole copy).

Scope note: engines/, sqlite-worker.ts, matcher/matcher-view, transactions.ts untouched — the entire fix is the `final` param (guard + re-entrant propagation), the `flush(true)` dispose call, the sealed public `flush` wrapper, and comment/doc hunks in `src/persist.ts`.
## [2026-07-22] — DAN-648: encode/decodeEntityRefs serialization integrity — `__proto__` no longer corrupts the ref-rebuild path, decode validates the full ref shape, `undefined` divergence documented (branch `tackle/dan-648-encode-decode-integrity`)

Three findings from the DAN-648 adversarial sweep over `store.ts`'s wire codec, each independently re-vetted with a failing repro before fixing. All three reproduced (no false positives). New spec: `src/encode-decode-integrity.spec.ts` (13 tests).

- [fix] **M1 (data-integrity + prototype-pollution-adjacent):** on the ref-REBUILD path of BOTH `encodeEntityRefs` and `decodeEntityRefs`, `result[key] = value` invoked the `__proto__` setter when an object carried an OWN enumerable `__proto__` key (JSON.parse / persisted data produces such keys) alongside a sibling `EntityRef`. Effect: the `__proto__` field was silently dropped AND the rebuilt object began inheriting from the supplied payload (its prototype was reassigned). The no-sibling-ref short-circuit (identity return) was never affected — confirmed. **Fix:** a shared `assignOwn(target, key, value)` helper that uses `Object.defineProperty` for `key === "__proto__"` (bypassing the setter, writing a real own enumerable data property, leaving `Object.prototype` intact) and plain assignment otherwise. `constructor`/`prototype` needed no special handling — they are data properties on `Object.prototype`, so plain assignment already shadows them as own props with no side effects (pinned by a passing regression test). Covers nested objects and array elements (recursion routes both through the same rebuild).
- [fix] **M2 (data-integrity):** the in-memory ref marker is a `Symbol`, but the wire format uses the plain string key `__pcn_ref`, reintroducing exactly the API-data collision the Symbol was chosen to avoid (Issue #13).
